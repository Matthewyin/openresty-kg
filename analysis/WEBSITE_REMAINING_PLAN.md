## 1. 实际 Bug：本轮 P0

### R01 特殊块内数据被误认成配置指令

主 Agent 已复现以下输入中的 `default`、域名、MIME、地址数据被列为 unknown：

```nginx
http { map $host $backend { default app; example.com foo; } }
http { types { text/html html; } }
stream { geo $allowed { default 0; 127.0.0.1 1; } }
```

这属于 Q3/Q8 的配置识别准确性缺陷，不是知识库缺指令。实施范围限主 Agent 已源码验证的 `map`、`geo`、`types`、`split_clients` 块内数据识别；具体允许的父 context、数据语法及块内特殊关键字依锁定源码确认，不能仅按块名称启用。

实施要求：

1. 在解析输出中明确区分普通指令与已知特殊块的数据项；块头本身照常匹配知识。沿用现有结构，采用最小必要标识，不新增通用语义分析器。
2. 数据项保留行列、父块和文本定位，并在网站标为“块内数据项，不参与指令匹配”。不得将它们算作 matched、unknown 或新增知识注册项。
3. `include` 及源码确认的特殊控制项按各块真实语法单独处理；include 必须保留外部内容未提供、未分析提示，不展开文件。控制项不能无依据作为普通数据吞掉。
4. 不得全局跳过 `default`、域名或百分比形态的名称；只在已知且有效的特殊块上下文内分类。未知父 context、未知嵌套块不能触发推断或静默忽略。
5. 保留缺分号、引号/块未闭合等结构错误；数据分类不能把错误输入变成整体成功。保持单项入口、Lua 边界、HTTP/stream 区分及 root 修复行为。

主要实施位置：`src/core/parser.mjs`、必要时 `src/core/contexts.mjs`、`site/app.mjs:154-160,201-221`，以及对应解析/匹配测试。主 Agent 核查锁定源码及真实解析边界，规划角色不重复研究。

验收判据：

- 上述三例及源码确认的 `split_clients` 合成例不再把合法数据报 unknown；数据项数与普通指令数分别可核对。
- 同一名称在特殊块外、未知父 context 内仍按既有规则处理，不因修复失去 unknown/context_required 等提示。
- 四类特殊块的有效/无效父 context、特殊控制项、include、注释/引号及结构错误均有针对性回归；测试预期以源码而非当前实现推导。
- include 的 not_analyzed 与网页提示保留；不新增文件读取或网络提交。
- 既有 root、Lua、单项与同名匹配回归通过；两份已提供样例回放仍保持原匹配结果，24/258是既有样例基线，不把数据项凑进 matched 数。
