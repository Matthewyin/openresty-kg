## 方案补充验收条件

- Q01：候选集合严格取本次各项 `match.candidates` 按 id 去重的并集；旧搜索、模块、context、阶段及“仅已核对项”筛选不得隐藏候选，初次提交完整展示且计数一致。
- Q02/Q03：解析行与目录中的候选点击都须打开对应 id；多条输入和单条歧义分别显示等待选择提示；未知上下文提示补充外层 http 或 stream。
- Q04：自动预览须同时满足恰一条解析完整指令、状态为 `matched` 或 `context_required`、恰一候选；明示唯一候选知识预览，保留 `context_required` 和 `registration_only` 未核实说明。错误状态禁止自动预览。
- Q05：文本输入、输入模式、查询 context/module 和示例填入均立即撤销旧解析结果、候选、详情及选中态；空白、未知、索引/网络失败明确显示当前状态。解析错误可保留本次诊断，但不发布可选候选。详情失败清除加载态和选中态，同时保留本次候选供重选。
- Q06：核查页面查询代次及详情请求序号覆盖 `querySingle`、详情和启动深链接；成功、失败和按钮/加载状态更新都必须防止迟到请求覆盖当前状态。分别检查编辑未提交、提交新查询、切换全目录及快速连续选候选。
- Q07：普通启动不默认预览；明确 URL id 可预览且标明链接指定条目。全目录入口恢复全局筛选、清空查询选中态及详情，并明确为全目录浏览；再次提交恢复当前候选模式。
- Q09：不改 `src/core/`、MCP、知识 JSON 或两份基线；核心解析测试通过不能替代 UI 验收。所有失败项应返回实施修正后再审。

## 最终审核

### UI-01 / P2：单项详情读取失败后丢弃已匹配候选（已关闭，以下为初审记录）

位置：`site/app.mjs:151-155`。方案第 5 项要求详情失败清除加载态和选中态，同时保留本次候选供重选。

触发：单项模式查询唯一候选（例如 more_set_headers），索引读取和匹配成功，但该条目的详情请求失败。`src/query/knowledge.mjs:114-125` 的现有调用链保留 `result.match`，并将状态改为 `knowledge_unavailable`。页面在第 151 行将该状态作为整次失败提前返回，第 155 行的 `setCandidates` 不会执行。由于提交开始已清空候选，目录最终为 0，不能点击当前候选重试。此结论来自实际调用链静态证据，未声称独立浏览器复现。

建议只在页面层区分“没有可用匹配结果”和“已有匹配但详情失败”：后者保留本次候选及明确失败提示，不自动预览、不保留选中态；仍在代次检查之后更新页面。无需改核心解析或知识契约。补充单项详情失败后候选仍可重选并成功恢复的 UI 回归。
